01项目概述

1.1 项目背景

校园是一个半封闭、高密度的生活场景：快递点集中、食堂与超市人流大、楼栋间距离远，学生在取快递、买饭、打印、搬重物等琐事上存在大量「跑腿」需求。与此同时，校内又有大量空闲时间充裕、机动性强的学生愿意有偿互助。传统上这类需求靠微信群、QQ 群、表白墙等分散渠道撮合，存在信息不透明、无资金担保、纠纷难处理等问题。

1.2 项目目标

构建一个面向单一/多校区的高校跑腿互助平台，实现「需求发布 → 接单撮合 → 在线支付 → 履约确认 → 信用评价 → 纠纷仲裁」的完整闭环。

1.3 产品定位

  • B2C2C 撮合平台：平台不自营跑腿，只做信息撮合、资金托管与信用担保。
  • 核心价值：可信（实名认证 + 资金托管）、高效（就近匹配 + 实时沟通）、安全（平台担保 + 双向评价）。

03功能需求

3.1 用户与认证模块

  • 注册登录：手机号 + 短信验证码，支持微信授权登录
  • 学生实名认证：姓名 + 学号 + 校园卡/学生证照片，对接学籍系统或人工审核，防非学生混入
  • 跑腿员认证：额外缴纳保证金（或信用分达标免押金）
  • 个人中心：余额、订单记录、信用分、常用地址

3.2 任务发布模块

  • 任务类型：代取快递、代买餐食、代打印、代寄件、代取外卖、代搬重物、代排队等（可配置模板）
  • 发布表单：类型、取件/送达地址（校内 POI 选择）、期望时间窗、悬赏金额、备注、是否回传凭证
  • 校内 POI 地址库：宿舍楼/食堂/快递点/教学楼/图书馆，比通用地图更贴合校内场景
  • 智能定价建议：按距离/重量/时段给出参考价

3.3 接单与履约模块

  • 任务大厅：列表 + 地图双视图，按距离、时间、类型筛选
  • 撮合机制：默认「先到先得」抢单；可扩展为平台派单（就近最优）
  • 订单状态机：待接单 → 已接单 → 取件中 → 配送中 → 已完成 / 已取消 / 纠纷中
  • 履约凭证：取件/送达拍照上传，支持超时提醒
  • 取消规则：接单后取消的违约金与信用分扣减

3.4 支付与结算模块

  • 资金托管（担保交易）：发布者悬赏金先冻结在平台，跑腿员完成并确认后解冻到账——这是平台可信的核心
  • 充值/提现：对接微信支付、支付宝；提现 T+1 审核
  • 平台抽成：佣金费率可配置（如 5%~10%），含优惠/补贴规则
  • 退款：取消/纠纷场景原路退回
  • 对账：日/月对账报表，资金流水可追溯

3.5 评价与信用模块

  • 双向评价：发布者 ↔ 跑腿员，评分 + 文字 + 标签
  • 信用分体系：认证、履约率、准时率、评价、违约记录综合计算；低信用限制接单/发布
  • 黑名单与风控：恶意刷单、虚假接单、频繁取消的识别与处理

3.6 消息与沟通模块

  • 订单内即时通讯（IM）：文字、图片、语音；中间号脱敏保护隐私
  • 系统通知：订单状态变更、超时提醒、结算到账（站内信 + 微信服务通知）
  • 客服工单：纠纷时介入，查看双方凭证与聊天记录

3.7 管理后台

  • 用户/认证审核、订单查询与干预、资金流水与对账
  • 任务类型与定价配置、补贴活动配置
  • 风控中心：异常订单、违规账号处理
  • 数据看板：日活、订单量、GMV、履约率、客诉率

三条不妥协的设计原则

  1. 资金域从第一天就强一致：账户余额变更走本地事务 + 幂等流水 + 对账，绝不用「最终一致」糊弄钱。
  2. 读多写少靠缓存和推送扛：任务大厅是推（MQ/WS）不是高频轮询，不让数据库硬扛。
  3. 通知类、状态类走事件异步，同步 RPC 只留给强一致读写，避免服务间网状耦合。

08演进路线与里程碑

架构演进三步

阶段一 · MVP（单体 + 领域分包）

单体应用内按领域严格分包，网关 + Redis + MQ 就位；资金域从第一天独立成「账户子域」并强一致。

阶段二 · 按痛点拆分

优先拆 pay-svc（资金独立扩缩容/合规）与 im-svc（独立技术栈/连接数压力）。

阶段三 · 全量微服务 + 平台化

K8s + 可观测平台 + 风控中心；按「痛点驱动」拆，不按教科书拆。
