01项目背景与问题定义

大学校园内,代取快递、代买餐食、代占座等跑腿需求高频且刚性：快递点离宿舍远、食堂排队久、图书馆一座难求。目前的解决方案主要是宿舍群 / 互助群里喊话,存在三个结构性问题：

🕳️

信息不对称

需求散落在几十个大群里,消息秒沉;有空余时间想赚外快的同学,根本不知道谁需要帮助。

⚠️

信任无保障

对方是谁、靠不靠谱完全未知;先给钱怕跑路、先跑腿怕赖账,取件码等敏感信息不敢给。

🤷

违约零成本

口头约定没有约束,放鸽子、坐地起价没有后果;长期参与者反而和投机者待遇相同。

问题定义

校园跑腿的本质是一个双边撮合市场,撮合效率不难做,真正缺的是「信任基础设施」——如何让两个陌生学生在 30 分钟内建立起「敢把快递码给对方」的信任。这是本产品的核心命题,也是与「群里喊话」的本质差异。

02目标用户与核心场景

角色画像核心诉求典型场景
需求方（发布者）时间被占用的学生:上课冲突、期末复习、生病卧床、不在校内快、稳、不被放鸽子;敏感信息（取件码）不泄露「在图书馆复习走不开,帮我把快递从驿站带过来,出 5 块」
供给方（跑手）时间碎片化的学生:顺路、没课、想赚零花钱顺路变现、赏金有保障不被赖账「反正要去食堂吃饭,顺手帮带一份,赚 6 块跑腿费」

双边角色同池互换——同一个用户这单是发布者、下单是跑手,这是校园场景区别于外卖骑手的最大特点,也是信用体系必须双向通用的原因。

03产品方案：三大信任机制

针对「信任」这一核心命题,产品设计三大机制作为护城河：

🎓 学籍实名认证

学号 + 校园卡拍照 OCR 认证,一人一号,头像带认证标。把「群里的陌生人」变成「可追责的同校同学」,信任的第一步。

🛡️ 赏金平台托管

发布任务时赏金先付到平台托管,发布者确认完成后才结算给跑手;纠纷可申请客服仲裁。双方都不怕被骗。

⭐ 信用分体系

初始 100 分,履约加分、违约扣分,分数直接挂钩接单权限与流量分配。让守信者获益、失信者出局。

异常分支

  • 跑手超时未履约：发布者可取消,赏金全额原路退回,跑手信用 -10,30 分钟内限制接单。
  • 发布者拒绝确认：跑手可申诉,上传凭证后进入 24h 倒计时,超时自动确认结算。

06信用分体系设计

信用分是产品的中枢规则,设计原则:违约成本远高于违约收益,守信有即时正反馈。

计分规则

行为分值变化设计理由
注册并完成学籍认证初始 100 分满分 120 起步留出奖惩空间
按时完成一单+2履约可积累,约 50 单可到金牌
收到 5 星好评+1鼓励服务质量,不只求完成
接单后超时 / 爽约−10违约一次 ≈ 白跑 5 单,痛感足够
投诉成立（欺诈/私自加价）−15恶性行为重罚,两次即出局

场景化规则：代占座的特殊约束

占座是校园场景特有的「道德灰区」需求,平台不禁止但设规则:占位保留上限 40 分钟,发布时必须写明,跑手拍照计时,超时被占走不算违约。用规则把灰区需求框进可履约的范围内,而不是假装它不存在。

07商业模式与冷启动

冷启动（单校验证）

  • 种子供给：先招 50 名「认证跑手」,前 100 单每单额外补贴 ¥2,保证广场「有单可接」。
  • 种子需求：在快递驿站、食堂门口张贴二维码,主打「下雨天/考试周」两个情绪峰值场景。
  • 单点打透：只做一所学校、跑通履约闭环后再复制——校园市场是天然的蜂窝结构,密度比广度重要。

盈利模式

阶段模式说明
早期免费 + 补贴不抽佣,先把双边密度做起来
中期按单抽佣 8–10%从托管赏金中抽取,校园客单价 ¥3–15,单均收入 ¥0.3–1.5
后期增值与广告加急置顶竞价、校园商家入驻（打印店/奶茶店官方代送）

10技术选型说明

  • 目标形态为微信小程序：学生触达成本最低、微信支付与登录原生打通、无需下载。
  • 本次交付为 Web 高保真可交互原型（零依赖单页 HTML）：保证评审链接域名固定、永久可访问、点开即玩,完整还原任务广场、发布、接单、订单流转、信用体系五大流程。原型已实现搜索、多维排序、localStorage 数据持久化、订单状态机（已接单→待确认→已完成）、送达凭证与双向评价的模拟闭环;认证、支付、托管、仲裁为模拟状态并在 UI 中明确标注。
  • 落地实现路径：微信小程序原生框架 + 云开发（云数据库 / 云函数 / 微信支付）,托管赏金走微信支付分账接口,学籍 OCR 调腾讯云 OCR。

11特色功能设计（事件驱动架构）

所有功能围绕同一套底层对象实现:User / Task / Order / OrderEvent / CreditEvent / SecurePayload / Poi。订单状态机统一为 OPEN → ACCEPTED → PICKING → DELIVERING → WAIT_CONFIRM → DONE,异常态 CANCELLED / EXPIRED / DISPUTED。所有状态变化写 OrderEvent,信用变化写 CreditEvent,信用分 = 100 + Σ(CreditEvent.delta),统计全部由事件聚合而非手工改数。

功能核心规则Demo 状态

落地顺序

  • 第一阶段（已在原型实现）：占座倒计时、微评价标签、信用事件账本、动态赏金建议——改动小、演示效果强。
  • 第二阶段（需后端与并发控制）：顺路拼单（事务接单）、取件码保险箱（KMS）、预约周期（定时 Worker）。
  • 第三阶段（需实时通信）：紧急接力广播（WebSocket/SSE）、信用护照分享。

质量保障

仓库内置 tests/smoke.test.js（jsdom,101 条断言）:覆盖注册与学籍认证、成员切换与一人一号校验、未认证权限拦截、状态机全链路、信用事件聚合、占座倒计时/延长/自动释放、取件码密文与访问日志、拼单校验一致性与整组回滚、完成/评价幂等、接力停播、排期触发、XSS 转义、刷新持久化等核心用例,npm install && npm test 一键回归;页内未捕获异常直接计入失败。

13健壮性与边界处理

功能越复杂,状态越容易失控。这一章记录已知的失效模式与处置方式——它们同样是产品设计的一部分。

风险处置
拼单绕过核心校验单接与拼单共用同一套前置校验（本人任务 / 学籍认证 / 信用分下限）与同一个接单事务;任一单不通过则整组回滚,占座倒计时与接力停播等副作用完整保留
取件码明文落盘草稿永不保存取件码;持久化状态只写密文字段,展示时解密、30 秒后抹除;生产换 AES-GCM + KMS 托管密钥
跑手替发布者确认演示按钮标注「代发布者确认」并在事件账本写入模拟标记;生产由发布者端发起,服务端校验操作者身份后才结算
重复提交重复结算所有状态转换加前置守卫:完成、确认、送达、取消、排期触发均幂等;评价加 reviewed 标记,一单只计一次信用
模拟数据污染真实流程模拟跑手接单同步从广场下架任务;草稿恢复时一并还原发布方式与排期选项
键盘与读屏不可用弹层打开即移入焦点、Tab 在弹层内循环锁定、Escape 关闭、关闭后焦点回到触发元素

工程基础设施

  • package.json:npm install && npm test 一键跑测试;.gitignore 忽略 node_modules,避免误提交依赖目录。
  • GitHub Actions CI:每次 push / PR 自动执行冒烟测试,回归失败即阻断。
  • 演示与生产的边界:所有模拟能力（认证、托管、OCR、接力广播、模拟跑手）在 UI 与事件账本中均有显式标注,上线时可逐项替换为真实服务而不改业务逻辑。

12账号与身份体系

信用分、履约记录、徽章都必须挂在账号上,所以「注册 → 认证」不是一道流程门槛,而是整套信任机制的入口。设计原则:进入极轻 · 认证即授予权益 · 权限与信用强绑定。

12.1 注册与认证流程

步骤设计关键决策
1. 微信一键登录wx.login 换取 openid,无密码、无手机号学生触达成本最低;openid 作为账号唯一键
2. 学籍实名认证昵称 + 学校 + 学院 + 学号 + 校园卡 OCR（模拟）一人一号:同学号重复注册直接拒绝,防刷号套取新人权益;校园卡按「最小必要」采集,核验后销毁原图
3. 权益发放认证通过 → 信用分 100 起步 → 开放发布与接单未认证可浏览但不可交易:既降低首次体验门槛,又守住信任底线

12.2 权限矩阵

能力未认证已认证说明
浏览任务广场 / 搜索 / 排序✅✅未认证也能完整感受产品价值
发布任务 / 接单跑腿❌✅拦截时给出认证引导,而非静默失败
赏金托管与结算❌✅涉及资金流转,必须实名可追责
信用分 / 徽章 / 校园足迹—✅信用挂在账号上,换设备同样跟随

12.3 成员与账号（演示能力）

  • 为什么 Demo 支持切换成员：跑腿是双边网络,评审时需要在一台设备上分别以「发布者」和「跑腿员」视角走通流程,切换比开两个浏览器成本低得多。
  • 数据隔离方式：每位成员各自持有独立的 CreditEvent 账本、订单、徽章与足迹,切换即整组替换;任务广场与取件码保险箱属于平台公共数据。
  • 生产形态：账号由微信 openid 唯一绑定,一设备一账号;演示版留下的是「切换成员」入口,上线前移除,仅保留「退出登录」。
  • 校园增长含义：同学用微信打开链接即可自助完成认证成为互助成员,认证即自带信用身份,天然是同校网络的裂变路径。
